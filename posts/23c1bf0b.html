C++ 对象模型探索

编译器说明

本文所有示例代码均在 Visual Studio 2026（MSVC 编译器）64 位环境下运行。如果使用 Linux 平台的 G++ 编译器，部分示例代码的输出结果可能有所不同。

类对象所占用的内存空间

sizeof 的使用说明

在 C++ 中，只要对象 a 的类型为 A，那么 sizeof(A) 和 sizeof(a) 的计算结果始终相同，与类的复杂程度无关。例如，类中包含成员变量、成员函数、静态成员变量、虚函数等，都不影响这两种写法结果相同这一结论。sizeof 计算的是类对象所占用的内存空间，包括非静态成员变量及可能存在的内存对齐填充，不包括静态成员变量和成员函数本身占用的空间。

空类对象

在 C++ 中，空类和空结构体的对象大小通常都是 1 个字节。

  • 对象大小：

    • 空类对象（class）：即使没有任何成员变量和成员函数，sizeof 的结果通常是 1。
    • 空结构体对象（struct）：与空类对象类似，sizeof 的结果通常也是 1。

  • 原因分析：

    • C++ 标准要求完整对象具有非零大小，以保证不同的独立对象拥有不同的内存地址。

  • 注意事项：

    • C++ 中 class 和 struct 的主要区别在于默认访问权限和默认继承权限，不影响空类型对象的大小。
    • C 语言标准不允许定义空结构体；GCC 等编译器可能通过扩展支持空结构体，其对象大小通常为 0 个字节。

带虚函数的对象

C++ 中，类的虚函数（包括虚析构函数）不占用类对象内部的数据内存空间（仅多占用一个虚函数表指针的额外空间），因为虚函数的函数体代码由该类的所有对象共享，单独存储于程序的代码区（或只读常量区），而类对象内部只存储一个指向虚函数表（vtable）的指针（vptr，32 位系统通常是占用 4 个字节，64 位系统通常是占用 8 个字节），而不是存储虚函数本身的代码；并且，无论类中有多少个虚函数，每个类对象内部永远只有一个虚函数表指针（vptr）；但多重继承的情况除外 —— 当一个类继承了多个含有虚函数的基类时，该对象内部通常会包含多个 vptr（每个含虚函数的基类子对象对应一个 vptr）。值得注意的是，虚函数表指针（vptr）是对象级别的，每个对象内部通常只包含一个隐藏的指针，用来指向该类的虚函数表（vtable）。

带成员函数的对象

C++ 中，类的成员函数（包括静态和非静态成员函数）不占用类对象的内存空间，因为同一个类的所有对象共享同一份成员函数代码，成员函数代码通常存储在程序的代码区中，而不是存储在每个类对象的内部。

带静态成员变量的对象

C++ 中，类的静态成员变量不占用类对象的内存空间，因为静态成员变量由该类的所有对象共享，单独存储于程序的静态存储区，而不是存储在每个类对象内部。

带非静态成员变量的对象

C++ 中，类的非静态成员变量占用类对象的内存空间，因为每个对象都有自己独立的非静态成员变量副本，用于存储对象各自的状态。

值得一提的是，若类中含有指针类型成员（如 char*、int*），该指针本身的大小与所指类型无关，而由目标平台的 ABI 决定：32 位系统通常为 4 个字节，64 位系统通常为 8 个字节。但这是经验规律而非标准保证，成员指针等特殊指针类型可能不同，且类中还会受内存对齐影响。验证指针类型成员占用内存大小的示例代码如下：

this 指针调整

核心概念

this 指针调整是 C++ 编译器在多重继承（及虚继承）场景下，为保证各基类成员函数中 this 指针正确指向对应子对象，而在指针转换和成员函数调用时自动插入的地址偏移操作。

  • this 指针调整的根本原因：

    • 在多重继承中，派生类对象由多个基类子对象按声明顺序拼接而成，只有第一个基类的子对象位于对象起始地址（偏移量为 0），其余基类子对象都位于非零偏移处。
    • 因此：
      • 一个 C++ 对象在逻辑上是 “一个对象”，但在物理上可以拥有多个不同的有效地址；
      • 不同基类上下文中的 this 指针必须指向各自的子对象起始地址，否则基类成员函数访问自身成员时会错位；
      • 于是编译器必须在 “派生类视角” 与 “基类视角” 之间做地址换算 —— 这就是 this 指针调整。

  • this 指针调整发生的时机：

    • this 指针调整并非随时发生，而是集中在以下几类指针语义转换的边界上：
    • 假设 A 和 B 是基类，C 派生类依次继承自 A 和 B
      场景说明调整性质
      向上转型（派生类 → 基类）C* 转 B*、C& 绑定到 B&非虚继承：编译期静态偏移；虚继承：运行期查表
      成员函数调用通过 C 对象调用继承自 B 的成员函数调用点插入偏移
      构造 / 析构期间构造 B 子对象时传入调整后的 this 指针编译器生成代码中完成
      向下 / 交叉转型dynamic_cast、static_cast 在继承层次间转换可能伴随（甚至多次）调整
      虚函数调用（thunk）虚函数表（vtable）中为调整 this 指针而生成的跳转桩代码运行期间接调整

  • this 指针调整的实现方式：

    • 静态调整（编译期确定）
      • 适用于非虚继承场景；
      • 基类子对象的偏移量在编译期由类布局完全确定，编译器直接在转换点或调用点把常量偏移加到指针上。
    • 动态调整（运行期确定）
      • 适用于虚继承场景；
      • 由于虚基类子对象在对象中的位置依赖于完整对象的实际类型（共享同一个虚基类子对象），偏移无法在编译期确定，必须运行期通过虚基类表（vbtable）或等价机制查询后调整。这也是 dynamic_cast 在虚继承下必须运行期工作的原因之一。

  • this 指针调整的关键特性：

    • 多地址性：同一对象在不同基类上下文中的 this 指针地址可以不同，但都指向同一个完整对象的某个子对象，语义上仍指向 “当前子对象”。
    • 对用户透明：源码层面 this 指针语义统一，this 指针调整全部由编译器自动完成，程序员无需手动加偏移。
    • 偏移来源分两类：非虚继承为编译期常量偏移；虚继承为运行期查表偏移（依赖虚函数表 vtable）。
    • 可能多次调整：在深层、多分支的继承图中做交叉转型时，一次转换可能需要连续施加多次偏移（比如经过多个中间基类）。
    • 与指针比较 / 相等性相关：调整后指针值可能不同，但通过正确转换回同一类型后应得到相同地址，这是 C++ 对象模型的一致性保证。
    • 空指针调整的保护：对空指针做向上转型（派生类 → 基类）时，标准要求结果仍为空指针（编译器需特殊处理，避免 nullptr + 偏移量 产生非空值）。
    • 虚函数 thunk：当通过基类指针调用派生类重写的虚函数时，若该基类子对象不在偏移 0 的位置，虚表中会放置 thunk（一小段桩代码），先调整 this 指针再跳转到真正的函数体。
    • 与 static_cast / dynamic_cast 的关系：向上转型（派生类 → 基类）可能伴随 this 指针调整；dynamic_cast 在运行期还能处理虚继承下的调整与向下转型。

  • this 指针调整与相关概念的区分：

    • 与虚函数表（vtable）：vtable 解决的是 “调用哪个函数”（动态绑定）；this 指针调整解决的是 “用哪个地址调用”（子对象定位），二者常配合（thunk 即二者交汇点）。
    • 与 reinterpret_cast：后者不做任何调整，跨继承层次使用会破坏对象模型；正确的向上转型（隐式转换、static_cast）才包含 this 指针调整。
    • 与对象切片：切片是值拷贝导致派生部分丢失；this 指针调整只是地址换算，不涉及拷贝。

总结

this 指针调整是 C++ 编译器为弥合 "派生类对象只有一个起始地址" 与 "多重继承（及虚继承）下各基类子对象位于不同偏移地址" 之间的矛盾，在指针 / 引用转换、成员函数调用、构造析构及虚函数派发等边界上，自动插入的地址偏移操作；非虚继承下为编译期常量偏移，虚继承下为运行期查表偏移，并辅以虚函数 thunk 与空指针保护等机制，最终向程序员呈现 "this 指针始终指向当前子对象 " 的一致语义。

什么是基类子对象

基类子对象是指派生类对象内部、由某个基类所贡献的那部分数据成员及其布局，它本身就是一个类型为基类的完整对象，只是被 "嵌入" 在派生类对象之中。正因为是独立子对象，它拥有自己独立的起始地址，可以被单独构造与析构、可通过基类指针访问；在多重继承场景下，一个派生类对象可能含有多个基类子对象（虚继承下则被共享为一个）。它与 "成员子对象" 同属完整对象的组成部分，区别仅在于来源：一个来自继承，一个来自类类型成员。理解基类子对象，也就理解了 this 指针调整的本质 —— 让基类成员函数中的 this 从 "派生类对象地址" 正确换算到 "对应基类子对象的地址"。在 C++ 标准中的，子对象（subobject）是一个层级概念，相关术语如下表所示：

术语含义
完整对象（complete object）独立定义的对象
子对象（subobject）完整对象内部的组成部分
基类子对象派生类对象内部，由基类贡献的那部分数据成员及其布局，类型为基类
成员子对象派生类对象内部，由某个类类型成员贡献的那部分数据成员及其布局，类型为成员类型
数组元素子对象数组中的每个元素

分析 .obj 文件

默认构造函数

核心概念

这里分析 .obj 目标文件是为了更好地理解默认构造函数语义。每个 .cpp 源文件都会编译生成一个 .obj（Linux 下为 .o）文件，最终编译器将这些目标文件链接生成可执行文件。构造函数包含无参数的默认（缺省）构造函数，传统上认为若未自定义，编译器会隐式声明一个 “合成的默认构造函数”。但需明确，编译器隐式声明的往往是一个 “平凡（Trivial）” 的默认构造函数（什么都不做，不产生实际机器指令代码，在 .obj 文件中不可见）；只有当类满足特定条件（如包含非平凡默认构造的成员对象或存在虚函数等）时，编译器才会为其合成出 “非平凡（Non-trivial）” 的默认构造函数（真正做事，产生实际机器指令代码，在 .obj 文件中可见）。

在 C++ 中，如果类没有自定义任何构造函数，编译器仅在以下 4 种必要情况下才会合成出一个有用（非平凡）的默认构造函数（即编译器不仅生成，还会执行特定操作）：

  • (1) 类中包含带有 “非平凡（Non-trivial）” 默认构造函数的成员对象（如果成员的默认构造函数是 “平凡（Trivial）” 的，编译器不会触发合成 “非平凡” 构造函数的动作）。
  • (2) 类继承自带有 “非平凡（Non-trivial）” 默认构造函数的基类（如果基类的默认构造函数是 “平凡（Trivial）” 的，编译器不会触发合成 “非平凡” 构造函数的动作）。
  • (3) 类中存在虚函数（因为需要初始化虚函数表指针 vptr，会合成 “非平凡（Non-trivial）” 构造函数）。
  • (4) 类继承自虚基类（因为需要初始化虚基类表指针 vbptr 等，会合成 “非平凡（Non-trivial）” 构造函数）。

注意：除此之外，若类内包含引用成员、const 成员或没有默认构造函数的成员对象，且这些成员没有类内初始化器（默认成员初始化器），则编译器合成的默认构造函数会被定义为 “已删除（deleted）”，无法直接使用。

平凡与非平凡构造函数

  • 平凡（Trivial）构造函数：编译器隐式声明但不执行任何实际操作（如不初始化类成员、不分配资源）的构造函数，通常不生成实际机器指令代码，常用于基本类型或空类。
  • 非平凡（Non-trivial）构造函数：需要执行实际初始化动作（如初始化虚函数表指针、调用类成员 / 基类的构造函数等）的构造函数，编译器必须为其生成真实的机器指令代码。
