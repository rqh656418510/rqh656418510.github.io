CentOS 7 升级 5.x 版本的内核

发表于 2025-03-16 更新于 2026-11-16 阅读次数： 评论数： 本文字数： 3.2k 阅读时长 ≈ 3 分钟

前言

CentOS 7 默认使用 Linux 3.10 内核。如果需要使用较新的内核版本，可以通过 ELRepo 第三方仓库安装 5.x 内核。本文以 kernel-lt 长期支持版本为例，演示如何将 CentOS 7 内核升级到 Linux 5.4.x，并设置为默认启动内核。

系统迁移建议

  • CentOS 7 已于 2024 年 6 月 30 日结束生命周期（EOL），官方不再提供安全更新和支持，建议迁移至 Rocky Linux 或 AlmaLinux 等发行版。
  • Rocky Linux 由 CentOS 创始人发起，以与 RHEL 保持 100% 缺陷级兼容为目标，适合追求原汁原味 CentOS 体验的用户。
  • AlmaLinux 由社区所有和管理，同样与 RHEL 二进制兼容，并提供 ELevate 工具支持从 CentOS 7 就地迁移。

注意事项

  • (1) 新旧内核可以并存，安装新内核时不要使用 rpm -Uvh 覆盖旧内核。
  • (2) 确认新内核能够正常启动、硬件驱动工作正常后，再考虑清理旧内核。
  • (3) 如果使用 NVIDIA 专有显卡驱动、DKMS 等第三方内核模块，升级内核后需要重新编译或安装对应模块。
  • (4) 建议保留至少一个可用的旧内核，以便出现启动问题时回退。
  • (5) CentOS 7 已经停止维护，继续使用时需要注意系统安全及软件仓库的可用性。
  • (6) CentOS 7 默认的 Glibc 版本是 2.17，无论是否升级系统内核的版本，Glibc 的版本都不会发生变化。

常见问题

显卡驱动兼容性问题

如果在 CentOS 7 升级 Linux 5.x 系统内核之前已经安装了 NVIDIA GPU Driver，那么系统内核升级成功后，建议先卸载原有的 NVIDIA 显卡驱动，再针对新版本的 Linux 系统内核重新安装驱动。尤其以前是通过 NVIDIA 官方提供的 .run 安装包部署驱动的情况，安装程序需要调用 GCC 编译器，将 NVIDIA 显卡驱动中的内核模块（Kernel Module）重新编译成与当前运行的 Linux 系统内核相匹配的模块。需要注意的是，CentOS 7 默认的 GCC 版本较旧（4.8.5），而 NVIDIA 显卡驱动可能对 GCC 版本有一定要求。此外，Linux 系统内核本身也是通过特定版本的 GCC 编译的。为了避免 GCC 编译器版本不兼容、显卡驱动内核模块编译失败等问题，建议在重新安装 NVIDIA 显卡驱动之前，通过 SCL Devtoolset 切换到与目标 Linux 系统内核构建环境兼容的 GCC 版本。比如，对于 5.4.278 版本的系统内核，可以使用 GCC 9.3.1（建议通过 SCL Devtoolset-9 切换 GCC 编译器环境）。需要注意，G++ 并非编译 NVIDIA 显卡内核模块的必要工具，真正参与内核模块编译的是 GCC。

特别注意

  • (1) 切换 GCC 版本并不是因为 Linux 内核升级后必须更换 GCC 版本，而是为了满足 NVIDIA 显卡驱动内核模块的编译要求。
  • (2) NVIDIA 显卡驱动安装程序会检查当前 GCC 版本，部分版本还会检查其与系统内核构建时 GCC 版本的兼容性。
  • (3) 应尽量使用与目标系统内核编译环境兼容的 GCC 版本，避免出现 Compiler version check failed 等问题。
  • (4) .run 安装包通常支持通过 /usr/bin/nvidia-uninstall 卸载旧显卡驱动，但如果原显卡驱动是通过 YUM 或者 RPM 安装的，应优先使用对应的包管理方式卸载，避免混合安装方式造成驱动文件冲突。
  • (5) 对于通过 .run 安装包部署的 NVIDIA 显卡驱动，可以使用 sh NVIDIA-Linux-xxx_xxx.run --add-this-kernel 命令，检查显卡驱动程序能否针对当前运行的系统内核环境生成相应的内核模块（即检查驱动程序与系统内核是否兼容）。
  • (6) 需要注意，使用 sh NVIDIA-Linux-xxx_xxx.run --add-this-kernel 命令，--add-this-kernel 参数主要用于为当前系统内核构建驱动安装包，不会真正执行显卡驱动的安装操作。

kexec 版本兼容性问题

CentOS 7 将内核升级到 5.4.278 后，原版 kexec-tools 2.0.15 在解析内核版本时出现兼容性问题：由于 KERNEL_VERSION 宏仅为补丁版本号预留了 8 位，而 5.4.278 中的补丁版本号 278 超过了 255，导致 kexec 报错 Unsupported utsname.release，进而无法加载 crash kernel，导致 kdump 启动失败。解决办法是下载 kexec-tools 源码 RPM 包，修改 kernel_version.c 中的版本解析逻辑，对超过 255 的补丁版本号进行饱和处理（设为 255），然后重新构建并安装 RPM 包。最终升级到修复后的 kexec-tools 2.0.15-52.el7，成功加载 crash kernel，kdumpctl status 显示 Kdump is operational，问题得到解决。值得一提的是，通过源码 RPM 包编译构建 RPM 包的详细步骤可以参考 《CentOS 7 修复 Flatpak 更新失败问题》，生成的 Kexec RPM 包可以从 这里 下载得到，直接使用 sudo rpm -ivh kexec-tools-2.0.15-52.el7.x86_64.rpm 命令安装即可。

系统无法睡眠、休眠问题

在 CentOS 7 上将内核升级至 5.4.278 后，suspend、hibernate、hybrid-sleep 命令（如下）均无法正常执行：系统看似进入睡眠（SSH 断开连接），但显卡风扇持续转动，整机并未真正低功耗或断电。原因在于 NVIDIA 闭源驱动的电源管理回调与 5.4.x 内核的睡眠流程配合失败 —— 驱动未能在冻结设备或切换 GPU 电源状态时正确响应，导致系统卡在 “用户态已停、GPU 未断电” 的中间态；其中 hybrid-sleep 因需同时完成写盘与挂起两步，对驱动配合要求更高，问题尤为明显。目前暂时没有找到合适的解决办法，只能暂时停用以下几个命令。
