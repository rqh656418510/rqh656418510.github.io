Linux 系统调整 Docker 的 dm.basesize 参数

发表于 2026-03-12 阅读次数： 评论数： 本文字数： 3.1k 阅读时长 ≈ 3 分钟

前言

使用 Docker 拉取 ComfyUI 镜像时，镜像层已经下载完成，却在注册层时出现 no space left on device。宿主机的 df -h 显示 Docker 数据目录所在文件系统仍有可用空间，df -i 显示也没有耗尽 inode。进一步检查发现，Docker 使用的是已弃用的 devicemapper 存储驱动，并通过 loop 设备提供存储；原有 Base Device Size 约为 10.74GB。在备份镜像和确认持久化数据后，将 dm.basesize 调整为 20G，重建 devicemapper 存储，再导入镜像。重建后 docker info 显示 Base Device Size 约为 21.47GB，ComfyUI 镜像最终拉取成功。值得注意的是，这是一份基于实际环境的排查记录；仅凭一次成功不能证明所有 no space left on device 都由 dm.basesize 引起；遇到同类问题仍应先检查文件系统、inode、Docker 存储池和具体错误日志。

重建 Devicemapper 存储会删除 Docker 管理的所有数据

  • 删除 Docker 数据目录会移除镜像、容器、Docker 网络和 Docker 管理的命名卷。执行前必须确认镜像归档可用、容器可重建，并备份需要保留的命名卷数据。
  • 宿主机 Bind Mount 的数据不在 Docker 数据目录中，通常不会随之删除；仍需核对挂载源路径，不能只凭容器名称推断数据位置。
  • dm.basesize 提高的是 devicemapper 设备的逻辑大小上限，不会增加文件系统的物理磁盘可用空间。loopback 存储的实际写入仍受宿主机文件系统可用容量约束。
  • devicemapper 已弃用，loopback 用法也不推荐用于生产环境。长期应规划迁移到受支持的存储驱动（如 overlay2）和文件系统（如 ext4、xfs）。

问题背景描述

拉取 ComfyUI 镜像时，报错发生在镜像层下载完成、注册镜像层的阶段：

当时检查到：

  • /var/lib/docker 实际位于 /usr 所在的 XFS 文件系统，该文件系统尚有可用空间。
  • inode 使用率较低，不是 inode 耗尽。
  • Docker 使用 devicemapper，原有 Base Device Size 为 10.74GB。
  • /usr 和根分区的 XFS 均显示 ftype=0，不能直接将这些位置作为 overlay2 的存储目录。

导出并验证带仓库名和 Tag 的镜像

  • 将镜像归档保存在 Docker 数据目录之外，并选择可用空间充足的文件系统。导出时使用 仓库名:Tag，不要只使用镜像 ID，否则在部分环境中导入后可能只得到 <none>:<none>。
  • 验证归档可读取，并记录 SHA-256。tar -tf 用于检查 tar 结构是否可读；SHA-256 值应保存下来，以便之后对同一个文件进行校验。

如果单个镜像导出时报 file integrity checksum failed，不要把不完整归档用于恢复。应定位并重新拉取（docker pull）损坏的镜像，再重新生成和验证镜像归档。

总结

  • devicemapper 已弃用，loopback 存储方式也不推荐用于生产环境。条件允许时，应规划迁移到受支持的 Docker 存储驱动（overlay2），并确保目标文件系统满足驱动要求。
  • 处理 Docker 镜像拉取时的 no space left on device 错误，不能只看 df -h 显示的结果来排查问题。应同时检查 Docker 使用的存储驱动、根目录所在文件系统、inode、devicemapper 的数据池与设备上限，并确认实际容器层遇到的限制。
  • 调整 dm.basesize 后，旧的 devicemapper 存储池不会因此自动变成新的大小；本次是在备份镜像和数据、停止相关服务后重建 devicemapper 存储，再确认新上限并恢复镜像。重建存储会清空 Docker 管理的数据，因此备份、验证和容器恢复方案必须先于删除操作。
